## Phase 6: scheduler (2026-10-28, defaults by me, change on objection)
- Scheduler stays opt-in (`SCHEDULER_ENABLED=false`). Four independent tasks: catalog-API refresh of owned cards (04:00), scraped fetch of owned cards (04:30), snapshot (06:00), full catalog import (Sun 03:00). Times are container time (UTC).
- Scheduled fetches are **unattended**: the fetcher fails a login/challenge page at once (`login_timeout` / `blocked`, "unattended: ...") instead of opening Chrome and waiting; the run then skips that site. Log in manually (Settings fetch) to restore the session; the next scheduled run uses it. If the fetcher is not running the run is recorded as a `skipped` job. No notification yet.
- Cap 300 cards per scheduled fetch, stalest first (by last attempt in `fetch_log`, never-tried first). No resume state: fetched cards become fresh, so the next run takes the rest.
- Boot catch-up: each task whose last `ok|partial` run is older than 24 h (7 d for the catalog; snapshot by `taken_at`) runs once, in order, in the background. Catalog catch-up is skipped until a first import exists. Catch-up uses the same cache-skip, so a manual fetch earlier the same day is not repeated.
- `jobs.trigger`: `manual` (default for API calls), `scheduler`, `catchup`. Older rows lack it (UI shows manual).

## Phase 8: export / import (2026-10-28, defaults by me, change on objection)
- JSON (`{"format":"moc-collection","version":1,"items":[...]}`) is the lossless format; CSV is flat for spreadsheets (money in integer cents, tags `;`-joined, `name/set/number` columns are read-only context). Import of an unknown `version` is refused.
- Import upserts on `stack_key`. Default mode `set` overwrites quantity and the editable fields (acquired, notes, tags), so re-importing a file is a no-op and an export doubles as a restore; mode `add` increments quantity instead. Rows that fail validation or reference an unknown card are reported by row number and skipped; the rest are applied (no all-or-nothing).
- Upload is the raw request body (no `python-multipart` dependency); 5 MB and 20k-row caps.

## Phase 8: code + security review (2026-10-28, defaults by me, change on objection)
- **Browser-origin guard** (`app/main.py`): CORS only stops a foreign page *reading* replies; a cross-site simple request (e.g. `text/plain` POST to the raw-body import, or body-less admin POSTs) still executes. Non-GET/HEAD/OPTIONS requests carrying an `Origin` not in `CORS_ORIGINS` get 403; requests without `Origin` (curl, scripts, tests) pass. `TrustedHostMiddleware` (`ALLOWED_HOSTS`, default `localhost,127.0.0.1`) blocks DNS rebinding. Test clients use `http://localhost`.
- Import body is read as a stream with the 5 MB cap enforced while reading (and `Content-Length` pre-checked), not after buffering. Bad field types in an import row (list `card_id`, non-string `created_at`) are per-row errors instead of a 500.
- `SaleIn.url` must be http(s); FE `safeUrl()` guards every `href` built from scraped/upstream data (blocks `javascript:`). `/api/admin/jobs?limit=` bounded 1-200.
- Checked, no change: search/filters use `re.escape` and typed params (no operator injection); product-match URLs validated to https + site host + path marker, and the fetcher independently enforces its per-site host allowlist; fetcher and Chrome CDP bind 127.0.0.1; mongo has no host port; `.env` is gitignored and absent from git; compose ports are `127.0.0.1`-only.
- Accepted, local-only: containers run as root; no rate limit on the API; CSV export does not escape leading `= + - @` in user notes (spreadsheet formula injection, only your own data); fetcher `/fetch` has no Origin guard (it only reaches whitelisted shop hosts).
- **RESOLVED 2026-11-02 by the toolchain bump (npm audit 0). History: npm audit (8 findings, all fixes are semver-major):** `vitest`/`@vitest/mocker`/`tinypool` (incl. the 2 critical "prototype pollution -> RCE" in tinypool worker options) and `vite`/`esbuild` (dev server readable by any website) are **dev-only**: never in the built bundle, the dev server is published on 127.0.0.1 only, and the exploit paths need attacker-controlled test config or a visit to the dev server while it runs. `react-router`/`react-router-dom` is shipped, but the advisories are an open redirect via backslash in user-supplied `<Link>`/`navigate` targets (the app has none: all targets are literals or ids) and SSR hydration (`deserializeErrors`, no SSR here). Fix needs vitest 4 / vite 8 / router 7, each a breaking migration of tooling that works; deferred until the next planned toolchain bump. Re-run `npm audit` then.
- Web container has a healthcheck (wget on :5180, 120 s start period for the first `npm install`). No prod nginx image: nothing is deployed.

## Alert notifications on macOS (2026-11-05)
- Lives in the host fetcher (`fetcher/fetcher/notify.py`), not in the app: the app runs in docker and cannot show a macOS notification, and the fetcher is already a long-lived host process. The backend is unchanged; the fetcher only polls `GET /api/alerts/events?unread=true` every 60 s.
- Dedupe by a high-water mark (`fired_at`) + notified ids in `~/.moc-fetcher/notified.json`, not by the event's `read` flag (that is UI state). State is written only after the notification was shown, so a failure retries on the next tick.
- First run seeds silently (user decision): the existing unread backlog is not announced. Afterwards one new event shows its text, several show "N new price alerts".
- `osascript` has no click-through; it needs notification permission for the host app that runs it. Off switch `FETCHER_NOTIFY_ENABLED=false`.

- Granularity: per stack, `acquired.price` = cents per copy (cost = price x qty). Mixed costs = weighted average; the form can take a total for N copies and stores the rounded per-copy average (error <= N/2 cents). Rejected per-copy lots: they break on quantity edits, remove and merge, and need much more UI. Limit: one type per stack, so a stack that mixes Pulled and Purchased copies cannot split P/L ex-pulled exactly.
- Adding copies to an existing stack re-averages the price when both are known and in the same currency; a different type or currency keeps the stack's own value and the add answers `type_conflict: true` (UI warns). Unknown old cost + known new cost takes the new cost.
- No migration: `type` null = "Not set", read-time default, counted as non-pulled. Notes reuse the item-level `notes`.
- P/L bug fixed: stacks without cost used to add their value but 0 cost (real data: 14 of 16 stacks, P/L showed ~+1,159 EUR instead of -32). P/L is now over stacks with cost and value only; the count without cost is shown and links to the "No cost" filter.
- Edit log `collection_edits` keeps full before/after of `acquired` for edit, bulk, merge, import and restore; restore applies a `before` and is itself logged. Never pruned. Alerts do not use cost. Snapshots keep `total_cost` and add ex-pulled / basis / pulled-value / missing-count.
- Export/import: JSON stays v1 (additive), CSV gets `acquired_type`. A `set` import of a file without `type` keeps the type already on the stack and logs an `import` edit when `acquired` changes.

## Collection list: cached valuation, server-side query (2026-11-05, roadmap Step 4)
- Measured first: `valuate()` cold = 190 ms (2000 stacks), 370-560 ms (5000), 760-870 ms (10000), and the old list endpoint paid it on every filter/sort/page click and every Summary/Dashboard call.
- Chosen: cache the whole valuation in process (`valuation_cache`, TTL 60 s + `bump()` from every write path) and run filter / sort / page / totals / facets as pure Python over the cached rows (5-34 ms warm). Rejected: Mongo-side filtering/sorting with valuation only for the page, because value, P/L, price range, needs-price, stale and the filtered totals need the valuation of every matched stack, so it saves nothing and creates a second code path. Rejected: a cache keyed on a Mongo fingerprint (max updated_at/count): price and FX writes touch several collections and `remove` does not stamp `updated_at`, so explicit bumps + TTL are simpler and bounded.
- Limits: in-process, so one uvicorn worker only; a missed bump shows stale values for up to 60 s (`VALUATION_CACHE_TTL=0` turns it off). Tests set the TTL to 0 by default (autouse fixture) because they write straight to Mongo. Cached rows are shared and must stay read-only.
- Filtered totals ride in the list response (`totals`), no separate endpoint: one request, always consistent with the page. Price range filters are per copy (value / quantity), unpriced stacks never match; "price stale" = the headline price's upstream `as_of` is older than `MARKET_MAX_AGE_DAYS`.
- Presets are stored in Mongo (`list_presets`, whitelisted keys, unique per scope + name), not localStorage: the user will also use the phone (Step 5) and a preset should not be lost with a browser. Built-ins are code. View mode (table | grid) is a per-device UI preference, so localStorage.
- Wishlist stays client-side (a few hundred rows at most): search + sort + presets + grid reuse the shared pieces, no pagination until it is needed.

## Phone scanning, slice 1 (2026-11-05, roadmap Step 5)
- **D1 = Tailscale** (user, after the trade-offs). Camera needs https on the phone. Options weighed: mkcert on the LAN (root CA to install on the phone, whose private key sits on the Mac and can mint certificates the phone trusts; port open to everyone on the Wi-Fi), a public tunnel (needs real auth first, rejected), plain http + native camera (no live view, unencrypted Wi-Fi). Tailscale: public Let's Encrypt certificate (nothing to trust on the phone), the Mac is not opened to the Wi-Fi (Caddy binds 127.0.0.1, `tailscale serve` is the only way in), device-level identity via the `Tailscale-User-Login` header Caddy checks. Costs: a Tailscale account and app on both devices; third-party coordination server. Never use Funnel (public).
- **No pairing tokens / QR login.** The tailnet login is the credential; the QR only carries the URL. Rejected: our own device tokens (more code, more state, weaker than a device-authenticated network).
- **Surface kept minimal**: the phone gets 4 scan endpoints, not `/api/collection` or `/api/cards`. `POST /api/scan/add` wraps the normal add so the phone cannot patch, delete, export or import. The DNS-rebinding guard is unchanged: the tailnet host is added to `ALLOWED_HOSTS` by `lan/lan.env` only, and in phone mode only that origin passes the Origin guard. A client cannot fake phone mode (it needs the secret, which only Caddy and the app know); a spoofed gate header is a 403.
- **OCR on the server, local** (Tesseract in the app image), not on the phone: no 10 MB wasm download, faster than phone CPUs, one place to tune. No paid API. Sparse mode on the name band beat one-line mode on synthetic names (8/8 vs 6/8), so both are run and the matcher picks. Accuracy on real card photos is **not measured yet**: tests use synthetic names only. Fallback is always typing the name.
- **Name -> versions**: exact `name_norm` match first (so "Pikachu V" does not collapse into "Pikachu"), fuzzy (difflib 0.75) only when nothing is exact, so a typo is shown as "guess" and never "high". All prints of the best names are listed (max 40 + "Show more"), owned first then newest set. Confidence is a hint; nothing is added without a tap.
- **Edition data gap**: pokemontcg.io has one Base Set Charizard with variant `holofoil`; 1st Edition / Shadowless / Unlimited are not separate. The picker flags sets that have such prints (`EDITION_SETS`) with "check the stamp". No new edition field or price per edition in this slice (prices would be wrong); open question for a later slice.
- **Acquisition remembered, last choice only** (condition, language, cost block) in the phone's localStorage. Duplicate = existing `collection.add` merge (same stack key); the add sheet says "adds one more copy to that stack (N total)".
- **Known limits**: no undo on the phone (slice 2 with batch mode; fix on the laptop), no price fetch triggered by a scanned add (the event carries `card_id`, so a laptop-side follow-up is easy), `apple-touch-icon` is an SVG which iOS ignores (the home screen icon may be a page snapshot), Add to Home Screen storage behaviour on iOS not verified.

## Phone scanning: card rectangle, number and print ranking (2026-11-07, roadmap Step 5 sub-step 1c)
- **Added `opencv-python-headless` + `numpy` to the app image (reverses the 1b "Pillow only" choice).** Pillow can warp a quad but cannot find one: contours, polygon fit and edge maps would be a few hundred lines of pure-Python geometry that is slow and fragile on glare. OpenCV is ~60 MB in the image, acceptable for a local single-user app. Failure of the geometry (exception or no quad) falls back to the 1b brightness stages, so scanning never depends on it.
- **Quad choice**: candidates from Canny edges and Otsu masks (both polarities), reduced to 4 corners (polygon fit, loosening epsilon until 4 points; a rotated box only as last resort because it ignores perspective), accepted when 6-98 % of the photo, within 16 % of 63:88, and not touching the frame on 2+ corners. A sleeve/toploader border cannot be told from the card's own inner art frame by shape, so the outer quad wins and a second read uses a 5 % inset.
- **Fields from fixed regions of the flat card**: number read digits-only (tesseract whitelist) in several regions x thresholds, majority vote (one read of a tiny crop is noisy: "127" came back as "727" or "797"; voting gave 14/15 correct on the real photos). The printed total is a weaker read than the number (412 for 128). Layouts differ (SV: set code + EN before the number; SWSH: regulation mark, set code, number, rarity dot; old cards: bottom-right), hence the region list. Set code is read letters-only and only counts when it equals a known `set.ptcgo_code`; a wrong read can therefore never exclude anything.
- **Ranking, not filtering**: each print gets signals (name, number, total, set); sort by count, name rank and newest set break ties; nothing is removed, so a misread number costs ordering, not the right card. `exact` is true only when one print leads and it agrees on number or set. Number + printed total find prints by themselves when no name is read (<= 12). Never auto-add (unchanged).
- **`ptcgo_code`** is now stored on sets and on `card.set` (pokemontcg provider). Existing rows lack it until the set is re-imported (idempotent); TCGdex provides no such code, so the signal is absent for that provider.
- **Measured on 15 real photos** (name-only baseline 14/15): name 15/15, number 14/15, top print correct and uniquely top 14/15 (the miss is sleeve glare on IMG_2994). Private accuracy test now also asserts a number read rate >= 80 %.

## Phone scanning: real-photo OCR (2026-11-07, roadmap Step 5 sub-step 1b)
- **Cause of "Couldn't read a card name"**: fixed top 20 % crop of the whole photo = table, not card. Measured 3/15 on the user's real photos (5 cards, 3 each; HEIC converted with `sips`).
- **Card detection in Pillow only** (no OpenCV/numpy added to the image): Otsu threshold on a 240 px thumbnail, median filter, bounding box; inverted when the frame edge is the lit part (light table); `None` (use the whole image) when the box is under 6 % or over 97 % of the photo.
- **Staged read, early stop**: top band (sparse + one-line), name strip, dark-pixel crops (cuts 90, 60: tesseract fails on a name drawn over busy art such as Chandelure's full art), whole card, whole image. The service stops at the first stage with an exact name of 4+ letters read at 55+ confidence. Typical photo 1-3 s, worst 4 s.
- **Matcher**: text after "Evolves from" is dropped (it names the previous stage and gave Lampent for Chandelure); a matched base name also offers its ex / V / VMAX / VSTAR / GX / BREAK forms because the ex glyph is read as "@x" or not at all. This reverses the slice-1 rule "Charizard ex is a different name, not offered".
- **Result 14/15 (93 %)**; remaining miss is glare on a sleeve. Accuracy test: `tests/test_scan_accuracy.py` reads `tests/private/scan_samples/` (git-ignored, with `labels.json`), skipped when absent, fails below 80 %. Everything else in the suite runs without the private photos.
- **Cost for P/L (user, 2026-11-06)**: a blank or 0 acquisition price means "no cost recorded": the stack's `cost` is `None`, it is excluded from P/L and counted in `cost_missing`. P/L only covers stacks with a cost above 0. Allocating a pulled pack's price over its cards is deferred.

## Slab label: locate, then read only it (2026-11-09, roadmap 5f slices 5 + 6 merged)
- **Why:** the position reader read 6 big tiles x 2 tesseract modes over the top third of the slab (~29 calls, 6-10 s) and still dropped / added cert digits. Cheap knobs (one psm, other widths) only traded grades away (measured, nothing kept).
- **What:** `slab.locate_label` finds the label as the first band of dense vertical strokes (text) in the top 42 % of the slab box (rows measured on the central columns), rejected when it starts below 22 % of the slab height (that is card art). Only that crop (1800 px wide) is read: psm 11 + 6 on the whole label, psm 6 on the right half (tesseract segments a tile better than a whole label), two digits-only reads of the lower-right corner (the cert), a digits-only read of the right column (grade = largest number), and the tight glyph crops by the tier word only if the column found no grade. ~7-10 calls, ~1-3 s. The tile reader runs only when no band is found, the crop is not a label, or the cert is not `cert_sure`; `_merge` lets its sure cert / grade fill what the cheap read lacked.
- **Cert rules** (`slabfields.CERT_SURE`): ACE 6 digits, PSA 8-9, BGS 10 starting `00`, CGC 10. ACE is 6 (not 5-7): a 7 digit run on an ACE label was always "year + card number" (2023 151). Reads from the cert corner count triple against the label lines. A grader word that fits no cert read (a logo read as "PSA" on an ACE label) loses to the cert length. A Beckett cert whose leading 0 became 9 / 8 / 6 is repaired and the raw read kept as `cert_alt`.
- **Unsure certs are never looked up silently:** `scan.slab_certs` returns only `cert_sure` reads (best, then `cert_alt`, at most 2 lookups; the 2nd only when the 1st is `not_found`). No sure read = no request to the grader; the answer carries `slab.cert_sure=false` and the phone card says so ("check the digits, then look it up"). Cost of a wrong guess is a stranger's card (PSA 2023151 = a 1976 baseball card).
- **Grade is secondary:** when the cert is found the page gives the grade, so a missing label grade does not trigger the slow path (it only loses the grade-mismatch tripwire).
- **Measured (24 photos, `tests/private/profile_slab.py`, host load ~5): baseline grader 17 / grade 15 / cert 12, 28.7 tesseract calls, 10.1 s per photo -> grader 21 / grade 12 / cert 20, 18.1 calls, 5.1 s per photo.** The fast path alone is 7-10 calls; the ~5 hard photos (tiny text: ACE 9 at distance, PSA 9 loose in a bag, Japanese PSA) fall back and cost ~26 calls. Tried and dropped: row strips for the cert (1/23), digits-only corner variants beyond two (union capped at ~16 reads), 2 anchors x 3 psms for the grade (+2 calls, no gain). Not met: grade >= 15 (label-only grade; PSA / BGS 9.5 grades under the tier word), calls <= 10 on average.

## Slab leftovers: grade column, level the label (2026-11-10, roadmap Step 5 item 2)
- **Why:** after "locate, then read only it" the label grade was read on 12/24 and ~5 photos still fell back to the slow tile read (IMG_3019: nothing read after 10 s).
- **Grade:** the right-hand column is read from two cuts and pooled (`GRADE_COLUMNS`: x >= 0.70 with psm 11 + 6, x >= 0.62 with psm 11 + 6 + 7). A tilted label clips a glyph in one cut and keeps it in the other (BGS 9.5 whole at 0.70, a lone PSA 9 at 0.62). `pick_grade`: a whole number beside its own X.5 read is the X.5 cut short (9 beside 9.5), and a 9.5 survives a MINT tier ("GEM" is often lost); whole numbers stay strict against the tier.
- **Level the label:** tesseract returns garbage on text tilted more than ~4 degrees (IMG_3019 was 8.5 degrees). `label_tilt` picks the rotation (+-12 degrees, 0.5 steps) that maximises the variance of the ink's row sums. It runs only as a retry when the plain read has no sure cert, before the tile reader. Leveling every label was measured worse (ACE 9 -> "PSA 2023 1519", BGS 9.5 -> 10: it moves reads that were clean) and is not done. Tried and dropped: per-row bands of the column (the plastic glare makes the crop one band), Otsu bright-rectangle angle (finds the whole crop).
- **Measured (24 photos, `tests/private/profile_slab.py`, host load varies):** label 22 -> 23, grader 21 -> 22, grade 12 -> 18, cert 20 -> 21; no new wrong reads. IMG_3019 10 s -> 5 s with cert. Open: ACE on a dark label (white text, IMG_3009: nothing read), grade None on 3012 / 3017 / 3019 / 3027 / 3030, the 3027 grader (PSA read as ACE) and 3030 cert digit. Avg time per photo 3.0 -> 3.5 s (extra grade reads and the retry).

## Slab identity from the cert (2026-11-08, roadmap 5f, user decision)
- **Why:** live slab test: slow (~20 s), raw-card match shown first, label read unreliable. A slab label already states card, set, number, year and variant, and the grader's cert page returns them exactly (ACE 158690 -> Radiant Charizard 011/078, Pokémon GO, 2022, Holo, 10 Gem Mint, subgrades, population).
- **Decision:** in slab mode the photo is read only for grader + cert (+ tier / grade); the card is identified from the cert page details, not from the card image. Raw-card OCR runs only as an explicit fallback. Same identifier rule as raw scans: name + number + printed total, set / year as a bonus, never auto-add.
- **Per-grader registry** (`providers/grading/`, documented in `docs/grading-cert-pages.md`): cert URL template, cert format, read method, fields. Pages differ per company, so each grader is its own small provider; a grader with no machine-readable page still gets the stored link.
- **Outbound requests:** only the cert number leaves the machine, only on a user scan, URL built from a fixed template with a digits-only cert (no SSRF), only providers call httpx, results cached in Mongo, no login, polite rate. Tests use saved page fixtures (no live network). Check each site's terms and robots before relying on it; a page behind a bot wall goes through the host fetcher or stays link-only.
- **Verified 2026-11-08/09 (real requests, details in `docs/grading-cert-pages.md`):** ACE = server-rendered HTML, plain httpx, no wall. PSA and Beckett = free report pages for anyone in a real browser (no account), but Cloudflare 403s plain requests, so they are read **only through the host fetcher** (real Chrome); fetcher down = link-only. CGC / SGC = not verified, link-only. PSA's official API needs an account OAuth login: not used.
- **Matching signals differ per grader:** ACE gives name + number + printed total (+ set, year, variant); PSA gives name + number, no total (+ year, Brand/Title set hint, variety); Beckett gives name + set name, no number. The match ranks with whatever the page gives; the result card says how exact it is (PSA / BGS never reach 'exact' on total alone; the user confirms).
- **Fetcher sites are data, not code (decided 2026-11-09):** the fetcher host allowlist (`sites.py`) merges the built-ins with `~/.moc-fetcher/sites.json`, re-read on every request, so a new grader needs no restart. `GET /health` reports the sites it knows; the app checks it before a fetcher-routed lookup and, when the grader's site is missing or the fetcher is down, degrades to link-only with a 'restart the fetcher: scripts/fetcher.sh restart' hint. The app cannot restart a host process (Docker) and must not. The one-time change that adds `/health` sites + `sites.json` needs one manual `scripts/fetcher.sh restart` (done: `scripts/fetcher.sh restart`). Unattended fetches (scans, scheduler) wait the 10 s challenge grace so a self-clearing Cloudflare 'Just a moment' passes, then fail `blocked`; they never ask for a login. Implemented in slice 2 (`app/providers/grading/`).
- **Unsupported graders are a registry entry, added when needed:** an unknown or link-only grader still stores grader + cert + the report link (when a template is known) and the label read; the cert cache records `status: link_only` per grader so unsupported graders that actually get scanned are countable (`GET /api/admin/...` or a log line). Adding one = verify its page in a browser (user shows it), add the registry entry + parser + fixture, add the site to the fetcher if needed. CGC template known (`cgccards.com/certlookup/{cert}/`); SGC template unconfirmed (no link until it is).
- **Set-first token matching (2026-11-09, slice 3b, after the first phone test).** Pages carry noise (BGS "Gardevoir ex SIR" = name + rarity, PSA set "POKEMON MEW EN-151" = brand + code), so exact name equality is gone. (1) The page set string + year resolve to up to 3 catalog sets (`slab.resolve_sets`): page and set words minus noise ("pokemon", "tcg", languages, rarity words, "and"), a set must be covered >= 60 % by the page words, series words ("Scarlet", "Violet", "Base"...) count half and a lone one needs the release year; the year and printed total are bonuses ("Paldean Fates" beats "Scarlet & Violet" for the BGS string). (2) Inside those sets a card matches when ALL its name words are among the page name words (accents stripped, punctuation splits, apostrophes join: "Mr. Mime", "Farfetch'd", "Flabébé"); only the longest matching catalog names stay ("gardevoir ex" over "gardevoir"). `name` signal only when the page has no other word beyond the NOISE list (so "Pikachu VMAX" never claims `Pikachu V` as an exact name). (3) No hit in the sets, or no set: global name match (regex on `name_norm` for the page's distinctive words), then the number + total fallback (Japanese). (4) Page rarity (SIR/SAR -> Special Illustration Rare, AR, HR, UR, SR, RR + full phrases, from name and variety) is a `rarity` signal, weight 2, compared as a word set with `card.rarity`; a bonus, never a filter. Number / total weights unchanged. The old TRAIL suffix list is now the NOISE word list.
- **Misread tripwires (slice 3c).** The cert response carries `warnings: [{code, text}]` (never blocking): `grade_mismatch` / `tier_mismatch` (label read vs page; `GET /api/scan/cert?grade=&tier=`, identify passes the label), `not_pokemon` (page found, no catalog hit, no Pokemon word in set / name / variety / language: the baseball card behind PSA:2023151), `cert_length` (ACE 5-7, PSA 8-9, BGS 10 digits; the lookup still runs). The UI (slice 4) shows "label says X / page says Y: check the cert digits". `GET /api/scan/certs/recent` (laptop only, not on the phone allowlist) lists the last cert lookups with the sets resolved, top matches, their signals and warnings.
- **Phone slab result card (slice 4).** In slab mode the pick step opens with `SlabResult`: one line from the page (`ACE 10 Gem Mint - Radiant Charizard 011/078 - Pokemon GO 2022 - Holo - cert 158690`), a how-exact badge, each `warnings` entry as "<label says X, page says Y>: check the cert digits.", the report link, and an edit form (grader buttons + digits-only cert -> `GET /api/scan/cert?grade=&tier=` again, which replaces the cards and the label read). Cases: `not_found` / `invalid` / `blocked` / `unavailable` / `link_only` each get a plain sentence; found without catalog cards (Japanese, not in the catalog, not Pokemon) shows the cert details and a name search prefilled with the page name. The candidate picker runs `quiet` (no "name read" wording: the page named the card). The add sheet is prefilled from the cert (grader, cert, grade from the label or else the page) and nothing is added before the last tap. Japanese slabs and binder pages stay out of matching: the user types.

## Scan accuracy pass 1 (2026-11-07, roadmap Step 5 item 4)
- **Measured first** (`tests/private/measure_accuracy.py`, gitignored, 42 raw photos, `ImageOps` not needed because `prepare` applies EXIF): top-1 / top-3 / in-list of the right print (name + number + printed total) and number read. Only 15 photos had number labels; the other 27 got number/total labels read off one photo per card by Claude (`labels_numbers.json`, not user-verified; Sprigatito MEP 061 and Celebi XY93 promos have no printed total).
- **The real lever was the number read, not the ranking formula.** On sleeved photos the number was read on 1 of 27: the inner-card quad search inside the flat sleeve is flaky (glare, art frame), and the outer sleeve flat puts the number line outside the fixed regions. Added `cardgeom.sleeve_crops` (fixed box x .10-.895, y .155-.915 of the sleeve flat, shifted 0 / -.075 / +.03) as extra flat candidates after the inner quad. Tried and reverted: shifts up to +.11 (no gain). A fixed box is a Vault-X-shaped guess; a real card-in-sleeve detector is the open fix.
- **Ranking:** weighted score (number 4, printed total 3, set code 3, HP 1, name 1) instead of a signal count, so a read number beats total + HP; `exact` still needs 2+ signals incl. number or set and a strictly better score than the runner-up. HP (already read) is a new weak signal (`card.hp` is a string); it separates ex / non-ex and reprints of one name but never makes a hit exact alone.
- **Misread totals:** a printed total no catalog card carries with that number is dropped for ranking (the number stays; dropping both lost the right print on Chandelure 137/412 for 137/128). The scan response still reports the read as read.
- **Result:** top-1 14 -> 19, top-3 15 -> 21 of 42; correct number reads 14 -> 20. Wrong-but-real pairs (4/63, 2/83) still rank a wrong print and can show `exact`; a name check on the number hit is the next step.

## Scan accuracy pass 3 (2026-11-10, roadmap Step 5 item 4)
- **Measured first** (same 42 photos): top-1 23, top-3 26, in list 38, name 41, number read 31 (25 right). After: top-1 23, top-3 27, rest unchanged.
- **Partial number signal.** OCR often loses the leading digit of the collector number. A print whose number ends with the read digits (read shorter than the number) gets `number_tail` (weight 2, between HP and the full number); `trusted` keeps the printed total for such a read instead of dropping it as unmatched. It is a hint: it is not `number`, so it never makes a hit `exact` (the user still picks). Rejected: treating it as a number match (a one-digit read ends many numbers: 177 and 187 tie for "7").
- **Why the unread number lines stay unread:** experiments showed the line is legible in the crops, so resolution / warp quality is not the cause (a direct warp from the photo at 1x and 1.5x read nothing more). Tesseract loses it to glare streaks, the star, copyright text and the card edge in the same crop, and isolating glyph blobs before OCR was brittle (digits merge with the slash on a global cut, comb-pattern backgrounds win on e-Cards). Nothing of that was kept. Next lever is not more tesseract tuning: image-match fallback on the artwork, or a small digit-shape model.
- **Not changed on purpose:** looser fuzzy name matching for fragments like "easel" (Sneasel 3033): catalog-wide false-hit risk without a better test set.

## Artwork match for unread number lines (2026-11-10, roadmap Step 5 item 4)
- **What:** when the name was read but the number line was not (or only one lone read), `services/artmatch.py` compares the photo's card art with the catalog art of the best-scored same-name prints (up to 80) and adds the weak signal `art` (weight 3, label "artwork") to every print within 20 % of the best score and >= 12 inliers. SIFT features of the art box (`providers/ocr/imagematch.py`), ratio test + RANSAC homography, score = inliers; rotation / scale / glare tolerant so sleeves and sideways photos work. Reprints that share art all get the signal (the user still picks by set / number). It is a hint: never `exact`, never auto-adds, skipped when the number was read by >= 2 votes.
- **Measured** (42 raw photos, `measure_accuracy.py`, same catalog): top-1 23 -> 31, top-3 30 -> ~39 (41 of 42 re-measured; the 42nd crashed on a tesseract timeout under host load). Lugia 3040/3042 rank 17 -> 2, Salamence 3048 38 -> 1, Charmeleon 3043 and Celebi 3049-3051 now top-1. Cost: first scan of a name downloads its prints' small images (8 at a time, a few seconds for names with 60+ prints), later scans of that name are cached.
- **Cache:** `art_cache {_id: image url, png: art crop}` in Mongo (~15 KB each, part of the normal backup). Only `providers/catalog/images.py` downloads; tests never touch the network (conftest autouse stub, synthetic art in `tests/test_artmatch.py`).
- **Threshold choice:** unrelated prints score <= ~8 inliers, a card missing from the catalog (Sprigatito MEP 061) best 5 -> no signal. Share 0.5 lost the true Lugia (27 vs a reprint's 101); 0.2 keeps it at rank 2.
- **Finding:** IMG_3037/3039 "Charizard 4/102" are Celebrations Classic Collection cards (25th logo), not Base Set. The matcher picks cel25c, which is right; the private label counts only base1, so 3037 still shows rank 32 in `measure_accuracy`. Not relabelled.
- **Not done:** wrong number reads (Lugia 84/64, Sprigatito 26/22) are not corrected by art, they just add a weaker vote; Sneasel 3033 name unread so there are no candidates.

## Scan accuracy pass 2 (2026-11-08, roadmap Step 5 item 4)
- **Card detection inside the flat sleeve.** `cardgeom.locate_card` searches 63:88 boxes (width 74-86 % of the sleeve flat) and scores each by edge strength along its four sides (integral images of the Sobel maps, clipped at the 99th percentile so glare streaks do not win). Without a size prior the card's own inner art frame wins (smaller box, stronger edges); a prior toward the larger box (`SIZE_PRIOR`) fixed that on synthetic sleeves (error < 5 px) and real ones. Returns None on a flat without clear edges (best <= 0 or < 1.4 x mean). It is the FIRST of the sleeve crops; the fixed Vault-X box and its shifts stay as fallback. Hard-set check (12 photos): top-1 1 -> 3 with the first version, 4 with the size prior. Real-photo cost: ~10 ms.
- **Tried and dropped:** wider number regions for the e-Card layout (Lugia prints the number at ~0.90 of the card height; reads stayed empty, glare and tiny glyphs), and 1.5x flats (630 -> 945 px wide) for the number read: no gain. The number-read misses left are OCR limits, not framing.
- **Wrong-but-real pairs (4/63, 2/83) and `exact`.** A name check cannot catch them (the name was right, the number pair was misread into another real print). The gate is read agreement: `CardFields.votes` (how many reads of the number region agree) is exposed in `read.votes`; a read with one vote cannot mark `exact` unless the top print also agrees on set code or HP. The ranking is unchanged and nothing auto-adds, so the cost is only that a lone correct read is not labelled exact (and in raw mode the slab label is then also tried). Measured: before, two wrong prints were marked exact (Sneasel 3032, Typhlosion 3053), after none. Typed lookups have votes 0 (unknown) and are unaffected.
- **Owner-prefix names.** A bare "Typhlosion" read now also brings "Ethan's Typhlosion" (`OWNER` pattern, like the ex / V suffix variants). Found because the new detector stopped the name stages early on the bare name where the old flats had read the full one by luck.

## Price scope: only tracked cards (decided and built 2026-11-09)
User: store and fetch prices only for cards the user selects into the collection (and fetches), and for wishlists (may be automatic, once a day), not for the whole catalog. Why: the catalog import writes prices for every card; it is noise, storage, and hides which prices the user actually cares about. How to apply: one `tracked_card_ids` rule (collection + wishlist); the import stores cards and sets only; refresh and snapshot touch tracked cards; answers (2026-11-09): (a) an untracked card shows "no price (not tracked)" with a one-card "Fetch price" action; (b) existing price rows of untracked cards are KEPT, no purge (so no purge script was built; rows go stale, nothing is lost). Adding to the collection or wishlist fetches that card's price once in the background. See roadmap 5h, pricing.md "Price scope".
